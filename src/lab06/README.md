## 1. Цель работы
Изучение системы аннотаций типов в Python, освоение механизмов обобщенного программирования (Generics) и использование протоколов для реализации структурной типизации.

## 2. Описание реализованных типов и контейнеров

### Реализованные Generic-классы
*   **TypedCollection[T]**: основной обобщенный контейнер. Он реализован для обеспечения безопасности типов (type safety), позволяя создавать коллекции, строго ограниченные определенным типом данных, который указывается при инициализации. Это исключает ошибки смешивания разных типов объектов в одном списке.

### Использование TypeVar и ограничения
В работе использованы следующие переменные типов:
*   **T**: свободный TypeVar для базовых операций коллекции (добавление, удаление, поиск).
*   **R**: используется в методе `map` для обозначения типа результата трансформации, который может отличаться от исходного.
*   **D (bound=Displayable)**: ограниченный TypeVar, разрешающий работу только с объектами, имеющими метод `get_info`.
*   **S (bound=Scorable)**: ограниченный TypeVar, разрешающий работу только с объектами, имеющими метод `get_score`.

### Протоколы и соответствие классов 
Вместо жесткого наследования использована структурная типизация через **Protocol**:
*   **Displayable**: требует наличие метода `get_info() -> str`. Ему соответствуют классы `BankAccount` и любые другие объекты, способные предоставить текстовое описание.
*   **Scorable**: требует наличие метода `get_score() -> float`. Ему соответствуют классы, имеющие числовое выражение (например, баланс счета или рейтинг).
*   Это позволяет контейнерам `DisplayCollection` и `ScoreCollection` работать с любыми объектами, соблюдающими данные контракты, без явного указания родительского класса.

### Сценарий 1. Тест find и Тест filter
**Цель**: Продемонстрировать работу методов поиска и фильтрации в обобщенной коллекции с использованием предикатов (Callable-объектов).

**Ход теста**:
*   **Метод `find`**: В качестве аргумента передана lambda-функция, ищущая клиента с именем «Марк». Программа вывела найденный объект. Сразу за этим был запущен поиск по условию (баланс > 100 000). Поскольку таких счетов нет, система вернула `None`. Это подтверждает, что аннотация типа `Optional[T]` (или `T | None`) работает корректно.
*   **Метод `filter`**: Использована функция-фильтр для отбора счетов с определенным балансом. Результат вывел список из двух подходящих счетов (Марк и Павел), демонстрируя итерируемость коллекции и корректную работу фильтрации.

### Сценарий 2. Тест map
**Цель**: Показать работу трансформации данных с изменением типа элементов коллекции (использование второго `TypeVar`).

**Ход теста**:
*   К коллекции объектов `BankAccount` был применен метод `map`, внутри которого lambda-выражение извлекало атрибут `owner_name` и приводило его к верхнему регистру (`upper()`).
*   **Результат**: Программа вывела обновленный тип коллекции — теперь это `list`, содержащий элементы типа `str`. Это доказывает успешную работу обобщения `TypedCollection[T] -> list[R]`, где `R` (тип результата) стал строкой.

### Сценарий 3. Тест Protocols (Displayable и Scorable)
**Цель**: Продемонстрировать концепцию «утиной типизации» (Duck Typing) через протоколы и работу ограниченных типов данных (`Generic[D, S]`).

**Ход теста**:
*   **Протокол Displayable**: Был вызван метод обработки, который ожидает объекты с методом `get_info`. Несмотря на то, что класс счета не наследуется от протокола явно, программа успешно распознала его и вывела информацию о счете Дарьи.
*   **Протокол Scorable**: Аналогичный тест для числовых показателей. Был вызван метод `get_score`, который вернул значение `300.0`.
*   Это подтверждает, что использование `Protocol` позволяет создавать безопасные интерфейсы для классов, которые формально не связаны друг с другом иерархией наследования.

## 4. Вывод
В ходе работы было изучено:
*   **Аннотации типов и их роль**: как способ сделать код более предсказуемым и облегчить поиск ошибок статическими анализаторами.
